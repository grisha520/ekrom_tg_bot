# План: перевод бота в клиентский режим (Telegram → потом МАКС)

## Цель
Сейчас бот — для менеджеров (менеджер вставляет сообщение клиента, бот отвечает
ему же). Нужно: **клиент сам пишет боту**, бот анализирует сайт ekrom, подбирает
технику и присылает **клиенту** PDF. Канал — пока Telegram, архитектура — с заделом
под перенос в МАКС. Отдельная задача — **выдержать поток клиентов** (масштаб).

---

## 0. Решения заказчика (блокеры — без них нельзя стартовать)

| Вопрос | Почему критично | Варианты |
|---|---|---|
| **Цены: розница или партнёрские?** | Сейчас всё берётся из партнёрского кабинета. Партнёрская цена = ваша закупка. Слать её клиенту — слив маржи. | а) розница с сайта (без логина); б) партнёрская + наценка формулой; в) ручной коэффициент |
| **PDF: свой шаблон или документ ekrom?** | Документ ekrom = партнёрская корзина (узкое место + чужой брендинг). Свой шаблон снимает оба. | свой PDF с вашим логотипом (рекомендуется) |
| **Лиды: что делать с заинтересованным клиентом?** | Иначе бот — тупик, бизнес не узнаёт о запросе. | уведомлять менеджера / собирать контакт / кнопка «связаться» |
| **Бюджет на инфраструктуру** | Бесплатный Groq и текущий сервер не потянут поток. | платный LLM-тариф, чуть больше сервер, домен |
| **Целевая нагрузка** | От неё зависит глубина масштабирования. | ~ сколько клиентов/сутки ожидается |
| **152-ФЗ (перс. данные)** | Если собираем контакты — нужно согласие. | галочка согласия + политика |

## 1. Этапы реализации

### Этап 1. Рефакторинг ядра и «шва» (фундамент + задел под МАКС)
**Зачем:** отделить бизнес-логику от транспорта (aiogram), чтобы (а) переиспользовать
в МАКС, (б) не дублировать код, (в) роли клиент/оператор жили в одном месте.
**Что:**
- Выделить **use-case слой** (`core/chat_service.py`): на вход (user_id, текст) →
  на выход «абстрактный ответ» (текст + опц. файл + список кнопок-действий).
- Вынести **тексты** в один модуль (шаблоны сообщений) — не в хендлерах.
- Ввести **роли**: `client` (открытый поток подбора) и `operator/admin`
  (обновить вход, статус, управление). Операторские кнопки клиенту не видны.
- Адаптер `telegram_app.py` оставить тонким: только приём апдейтов и рендер.

**Оценка:** 2–3 дня. **Риск:** низкий.

### Этап 2. Свой генератор PDF (отвязка от партнёрской корзины)
**Зачем:** текущий PDF = очистка+заполнение **общей** корзины ekrom (один сеанс на
всех → строго по очереди → не масштабируется) + партнёрский брендинг/цены. Свой PDF
из уже собранных данных это убирает и **распараллеливает**.
**Что:**
- Генерация PDF из данных подбора (`reportlab` или `weasyprint`): название, цена
  (с учётом правила ценообразования из п.0), характеристики, фото, ссылка.
- Брендинг магазина (лого, контакты), итог, дисклеймер.
- (Позже — задел под «несколько вариантов»: бюджет/оптимум/премиум.)

**Оценка:** 3–4 дня. **Риск:** средний (вёрстка PDF, шрифты-кириллица, картинки).
**Эффект:** снимает главное узкое место по конкурентности.

### Этап 3. Кэш каталога + наличие (ядро масштабируемости)
**Зачем:** сейчас **каждый** запрос гоняет Playwright по сайту (3–15 с, нагрузка на
ekrom, хрупкость к смене вёрстки, последовательность из-за одного браузера). При
потоке клиентов это не живёт.
**Что:**
- Периодический **краулер** (cron) складывает каталог в локальную БД (SQLite →
  при росте Postgres): товары, характеристики, цены, наличие, фото.
- «Горячий путь» клиента **читает кэш** (мгновенно, параллельно, без Playwright).
- Обновление: по расписанию (напр. каждые N часов) + точечная проверка наличия
  перед PDF, если нужна высокая точность.
**Альтернатива (легче):** кэш только результатов смарт-фильтров на TTL — меньше
работы, но и выигрыш скромнее.

**Оценка:** 5–8 дней (полноценный краулер+БД) / 2–3 дня (лёгкий кэш).
**Риск:** средний. **Эффект:** ×5–10 скорость, устойчивость, держит поток.

### Этап 4. Клиентский режим и UX
**Зачем:** клиент ≠ менеджер: другой тон, ошибки, ожидания.
**Что:**
- Открыть поток подбора всем (гейтить только операторские функции).
- **Онбординг** `/start`: что умеет, как писать, пример. Дружелюбный тон, эмодзи.
- **Пустой/мусорный запрос** («привет», стикер, не по теме) → мягкая подсказка,
  а не «❌ не удалось разобрать».
- **Понятные ошибки** (без «проверьте GROQ_API_KEY»).
- **Лиды:** уведомление менеджеру о живом запросе + кнопка «связаться с менеджером»
  (+ согласие 152-ФЗ, если собираем контакт).
- Дисклеймер «автоподбор, наличие/цену подтвердит менеджер».

**Оценка:** 3–5 дней. **Риск:** низкий.

### Этап 5. Масштаб, лимиты, надёжность
**Зачем:** «выдержать поток клиентов» и не падать.
**Что:**
- **Rate-limit на пользователя** (N запросов/час и /сутки) + общий предохранитель.
- **Бюджет-гард по LLM-токенам** (дневной), чтобы спам не выжрал лимит у реальных.
- **LLM:** перейти на **платный тариф Groq** или добавить запасного провайдера;
  рассмотреть кэш одинаковых запросов и более дешёвую модель на простой разбор.
- **Очередь/воркеры:** если оставляем Playwright где-то — пул контекстов, лимит
  конкурентности; основную нагрузку уводим в кэш (Этап 3).
- **Redis** — rate-limit, кэш, очередь (одна зависимость закрывает три задачи).
- **Мониторинг:** метрики (запросы, успех/неуспех, время, токены), алерты.
- **Бэкапы** `.env`, БД, сессии ekrom. **CI** — прогон тестов на push.

**Оценка:** 4–7 дней. **Риск:** средний.

### Этап 6. Сервер / инфраструктура
**Зачем:** под клиентский поток и под будущий webhook МАКС.
**Что:**
- **Апгрейд VPS** (под краулер + бот + Redis + браузеры): ориентир 4 vCPU / 8 ГБ.
- Разнести процессы: бот, краулер (cron), Redis; логи/ротация.
- **Домен + TLS** (Let's Encrypt + reverse-proxy) — нужно для webhook МАКС позже,
  и полезно для вебхуков/мониторинга уже сейчас.
- Безопасность: **сменить root-пароль / SSH-ключи** (давний долг), фаервол.

**Оценка:** 2–3 дня. **Риск:** низкий.

### Этап 7. Задел под МАКС (отдельный будущий блок)
- Заказчик проходит регистрацию (см. `docs/МАКС_памятка_заказчику.md`), даёт токен.
- Пишем адаптер `max_app.py` поверх REST API МАКС, ядро (Этапы 1–5) переиспользуем.
- Webhook на готовом домене/TLS (Этап 6).
**Оценка адаптера:** ~6–9 дней (см. отдельную оценку). **Сейчас не делаем.**

## 2. Масштаб: как считать «достаточно клиентов»

Узкие места по нарастанию:
1. **LLM-токены** (сейчас бесплатный Groq ~200k/сутки = ~130–180 сообщений/сутки).
   → платный тариф снимает потолок. **Это первый ограничитель.**
2. **Один сеанс ekrom/браузер** (всё последовательно). → Этап 3 (кэш) убирает
   Playwright из горячего пути, и подбор становится параллельным.
3. **CPU/RAM сервера** под краулер+браузеры. → Этап 6 (апгрейд).

**Ориентиры пропускной способности:**
- Сейчас (как есть): ~130–180 сообщений/сутки, по сути последовательно.
- После Этапов 2–3 + платный LLM: **сотни–тысячи сообщений/сутки**, ограничение —
  LLM-бюджет и сервер, а не архитектура.

## 3. Рекомендуемый порядок и общая оценка

**Минимально жизнеспособный клиентский бот (MVP):**
Этап 1 → 2 → 4 (+ базовый rate-limit из 5) → 6 (домен/сервер по необходимости).
**≈ 10–14 рабочих дней.** Уже можно открывать клиентам при умеренном потоке.

**Полная версия под нагрузку:**
+ Этап 3 (кэш) + Этап 5 (масштаб/мониторинг) + платный LLM.
**Суммарно ≈ 3–4 недели.**

**МАКС** — отдельным блоком после, когда заказчик даст токен (+6–9 дней адаптер).

---

## 4. Что НЕ входит (держим на карандаше)
- «Несколько вариантов на позицию» (бюджет/оптимум/премиум) — после базовой версии.
- Многошаговый диалог-уточнение («дешевле», «другой цвет»).
- Расширение характеристик подбора (объём, загрузка, класс энергопотребления).

## 5. Ближайший шаг
Ответы заказчика на 6 вопросов из раздела 0 (особенно **цены** и **PDF**) — от них
зависит объём Этапа 2 и вообще запуск PDF для клиента. После этого фиксируем MVP-скоуп
и начинаем с Этапа 1 (рефакторинг — безопасен и нужен в любом раскладе).
