## 1. Наличие: не использовать товар, которого нет — ✅ сделано 10.09

**Сейчас.** Кандидаты для комплекта берутся из кэша целиком
(`pipeline._candidates_for_spec` → `cache.query_category`), и ни `kit_builder`,
ни `selector` поле `in_stock` не смотрят. Проверка есть только в старом пути
одиночного подбора. Контрольная сборка 10.09: **16 из 50 позиций — «нет в
наличии»** (Lex GVG 642-1, Kuppersberg HF 609 W, Midea MO611107YGB…).

Побочный эффект: это, вероятно, часть причины, почему Lex выигрывает 25 из 47
сценариев — его дешёвые позиции часто именно те, которых нет.

**Что делать.**
1. Жёсткий фильтр на входе: в `_candidates_for_spec` (или в самом
   `query_category` параметром `in_stock_only=True`) отбрасывать `in_stock == False`.
   `None` (14 товаров, статус не прочитан) — оставлять: выдумывать отсутствие нельзя.
2. Страховка в `kit_builder.build_brand_kit`: не брать товар с `in_stock is False`
   даже если пришёл из другого источника (живой обход).
3. Тест: комплект никогда не содержит `in_stock=False`; при отсутствии товаров в
   наличии позиция уходит в «не нашлось у бренда», а не подменяется отсутствующим.
4. Перепрогнать E2E-сьют и сравнить распределение брендов до/после.

**Где:** `pipeline.py` (~строка 700), `ekrom/catalog_cache.py`, `matching/kit_builder.py`.
**Объём:** S. **Риск:** покрытие комплектов у Lex просядет — это честно, а не регресс.

## 3. Приоритет сборки по плашке «Хит продаж» — ✅ сделано 10.09

**Сейчас.** Плашка в данных (`Хит продаж == Да`, 158 товаров у 5 брендов). При
ранжировании внутри позиции кандидаты сортируются по совпадению характеристик и
цене (`selector.ranked_candidates`), хит не учитывается.

**Что делать.**
1. В ранжировании кандидатов позиции добавить признак `is_hit` как **старший
   ключ сортировки среди прошедших фильтры**: сначала хиты, внутри — прежний
   порядок (характеристики → цена). Хит не должен обходить требования клиента
   (цвет/размер/тип) — он только выбирает между одинаково подходящими.
2. Цена хита **не ограничивается** (решение заказчика 10.09): хит встаёт первым
   среди равно подходящих независимо от стоимости.
3. Выбор бренда для комплекта оставить по итоговой цене (правило «полный комплект
   по выгодной цене»); хиты влияют только на выбор модели внутри бренда.
4. В сообщении клиенту помечать позиции «🔥 хит продаж» — это и продаёт, и
   объясняет выбор.
5. Тесты: хит побеждает при равной цене; не побеждает при нарушении требования;
   порог цены работает.

**Где:** `matching/selector.py` (ranking), `messenger/client_ux.py`, `config.py`.
**Объём:** M.

3. Тест на вытяжки без атрибута встраивания и на дефолт 600.

**Где:** `matching/selector.py` (`_product_width`, фильтр ширины по типу техники).

## 7. Почему не распознался текст (чат с Сергеем)

**Что нужно от заказчика:** сам текст сообщения (скрин или копия) и, если есть,
ответ бота. Без него анализ невозможен.

**Что сделаю, получив текст:** прогоню через `parse_message` на проде, найду
этап, где потерялось (разбор LLM / сокращения / категория / фильтры), и починю
так же, как «п/м 450» и «варка 3-х комф.» — детерминированно, с тестом на сам
текст. Вероятные кандидаты по опыту: сокращение, которого нет в словаре;
латиница в русском слове; характеристика, «утёкшая» в соседнюю позицию.

**Объём:** S–M, зависит от причины.

## 8. Управление брендами и акциями через панель админа

**Сейчас.** Пять брендов зашиты в коде (`kit_builder.TARGET_BRANDS`). Акции
приходят только из краула раздела «Акции»; выключить одну или добавить свою
нельзя. Механизм «админ управляет из бота» уже есть — список менеджеров
редактируется кнопками в Telegram.

**Предлагаю в два этапа — второй только если первого мало.**

**Этап A — из бота (без веб-панели), объём M:**
1. Бренды — таблица `settings_brands` в `catalog.db` (или `data/brands.json`),
   при старте загружается вместо константы. Команды админа: `/brands` — список,
   кнопки «➕ добавить», «➖ убрать», «🔕 без акций» (флаг как у Lex).
2. Акции — к `promo_campaigns` добавить `enabled` (по умолчанию 1) и
   `manual` (добавлена вручную, краул не трогает). `/promos` — список активных с
   кнопками «выключить/включить». Ручная акция — через пошаговый диалог
   (бренд → механика → тарифы → срок) либо JSON-файлом.
3. Краул при `replace_all` **сохраняет** `enabled` и не удаляет `manual`.
4. Тесты на загрузку брендов из хранилища и на сохранение флагов при краула.

**Этап B — веб-панель, объём L:** отдельное приложение (FastAPI + простая
страница), вход по паролю/токену, те же операции плюс просмотр логов подборов.
Нужно только если управлять будут не через Telegram или людей станет много.
