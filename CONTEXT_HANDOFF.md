## Что это
Telegram-бот подбора техники **ekrom.ru**. Клиент пишет запрос → бот подбирает по
каталогу → присылает PDF. Бот: **@ekroom_bot**. Прод на VPS.

## Стек
- Python 3.12 (сервер) / 3.13 (локально), пакет `max_ekrom_bot`, aiogram 3.20 (long polling).
- **YandexGPT** Lite (парсер) + Pro (резолвер категорий + attr-маппер). Playwright (ekrom).
- reportlab (PDF). SQLite (кэш каталога + история + метрики). ~191 тест pytest.
- Ядро `pipeline.py`: parse → резолвер → attr-mapper(схема) → кэш → селектор → enrich → PDF.

# АКТИВНАЯ ЗАДАЧА: «Комплекты 5 брендов по акциям»

**Суть (от заказчика):** переориентировать бота — работать **только с 5 брендами**
(Korting, Maunfeld, Midea, Lex, Kuppersberg), собирать **комплекты техники из ОДНОГО
бренда** на основе **раздела «Акции»**, учитывать **дизайн-совместимость**, и выдавать
**PDF, визуально идентичный** документу корзины ekrom (эталон прислан).

## Решения заказчика (приняты)
1. **Полная замена** — бот работает ТОЛЬКО с 5 брендами и комплектами (текущий подбор
   по всему каталогу отключается; инфраструктура переиспользуется с фильтром брендов).
2. **Данные — бот сам с сайта** (краул акций + характеристики; Excel НЕ дают).
3. **Итог акции считает бот** (кодируем механики кампаний).
4. **PDF — свой генератор** (reportlab), но **точь-в-точь как эталон** (НЕ брать cart_pdf.php).

## Разведка сайта (факты)
- **2053 товара** 5 брендов: korting 659, lex 554, maunfeld 526, kuppersberg 183, midea 131.
- **«Акции» = набор кампаний**, каждая — своя страница `/catalog/aktsii/<slug>/`; верхняя
  `/catalog/aktsii/` карточек товаров не содержит. Многие кампании комплектные:
  `korting_skidki_pri_pokupke_komplekta`, `kuppersberg_skidka_na_komplekt`,
  `kuppersberg_kaskadnaya_skidka`, `maunfeld_soberi_svoyu_skidku`, `..._v_podarok`.
  Механики РАЗНЫЕ: скидка на комплект / каскадная (чем больше позиций — тем больше %) /
  техника в подарок.
- **Дизайн-коллекция в данных почти отсутствует:** «Коллекция» лишь у 28 товаров, «Стиль»
  у 364. → совместимость по дизайну надёжно не вытащить; эвристика: **бренд + цвет/финиш +
  стиль/тип управления**. Честно предупредить, что это «визуально сочетается», не «одна линейка».
- **Эталонный PDF = документ корзины ekrom** (`cart_pdf.php`): шапка «Корзина от …»,
  карточки (фото+название+артикул+характеристики+цена, «Скидка −30%» + старая зачёркнута),
  блок «Итого» (Сумма без скидки / Индивидуальная скидка −X% / Сумма со скидкой), сервис-
  пункты, карточка менеджера (имя/почта/телефон), адреса шоурумов. Дамп текста:
  `scratchpad/ref_pdf_dump.txt` (если сохранился), сам файл был в Downloads/document (2).pdf.

## Ключевой вопрос (Ф1) — ОТВЕТ ПОЛУЧЕН
**Корзина ekrom НЕ применяет комплектную скидку автоматически.** Живой тест
(логин → добавил в корзину Korting духовой шкаф 45 990 ₽ + варочную панель 25 490 ₽
из акции «Каскадные скидки» → очистил): **ИТОГО = 71 480 ₽ = сумма цен, без скидки**
(каскад −25% на наименьший НЕ применился). Значит «Индивидуальная скидка −X%» в эталонном
PDF ставит МЕНЕДЖЕР вручную. → **% берём из правил кампании (закодированы в датасете Ф1),
не с сайта и не из корзины.** На странице кампании per-товар старой/промо-цены у
комплектных акций тоже НЕТ (проверено: 0 из 21). Подтверждает решение заказчика №3 «итог
считает бот».

## СЕССИЯ 13.08.2026 — сверка с живым сайтом и починка сроков акций

Проверили раздел «Акции» вживую (25 кампаний на сайте, **14 наших пяти брендов**;

   предлогов — позиционно.
2. **Срок берём с плитки раздела, а не из прозы правил.** У «Maunfeld: подарок за
   новинку» в тексте стоит 05.08.2026, но сайт продлил акцию до 31.08.2026 и показывает
   её активной — плитка отражает поля активности Bitrix и надёжнее текста.
3. **Истёкшие/не начавшиеся акции отсекаются** в `PromoStore.campaigns_for_brand`
   (`period_to >= сегодня`, `period_from <= сегодня`; без дат — считаем действующей).
   Проверено на живом датасете: сегодня активны все 14, «из будущего» (15.10.2026)
   остаются 3 — с открытым концом и до 31.12.
4. **Новая акция Korting «Формула выгоды»** (до 30.09.2026) — подарок-лестница:
   2 прибора → вытяжка KHI 6393 N, 3 → духовой OKB 3810 FGN, 4 → ПММ KDI 45140.
   Под неё в `parse_gift` добавлен шаблон «при покупке N приборов … в подарок … МОДЕЛЬ»
   (модель ПОСЛЕ слова «подарок», несколько порогов). Оцифрована, участвует в выборе
   выгоднейшей акции.
5. **Исключения ищутся в границах предложения.** Было окно ±90 символов, и фраза
   «участвует весь ассортимент (**отдельностоящая** и встраиваемая). В акции не
   участвуют: …» ложно исключала всю отдельностоящую технику. Добавлены формулировки
   «двухконфорочные» → домино и «отдельностоящая микроволновая печь» → соло-СВЧ.
6. **`scope` стал трёхзначным:** `all_brand` / `listed` / `unspecified`. Раньше всё, где
   нет слов «весь ассортимент», считалось `listed`, хотя витрина кампании — это лишь
   21 карточка, а не состав акции. Теперь `listed` ставится только по явному «участвуют
   только …», и лишь тогда движок сверяет позиции со списком участников
   (`PromoStore.campaigns_for_brand` отдаёт `listed_urls`, сравнение по пути URL).
   На живых данных `listed` сейчас нет ни у одной кампании — поведение консервативное.
7. **Cron на акции:** `deploy/install-cron.sh` (каталог 04:00 + акции 04:40).
8. **Подарок-лестница выбирается по достижимому порогу.** `_preferred_promo_models`
   теперь принимает число разных категорий запроса: у «Формулы выгоды» выдаётся ровно
   ОДИН подарок, а без учёта порога в предпочтение попадали все три модели сразу и
   комплект уводило к моделям, которые подарком не станут (для порогов по СУММЕ
   покупки цены заранее неизвестны — там оставляем все модели).
9. **Клиент видит, по какой акции посчитано и до какого числа.** `ComboResult` несёт
   `campaign_title`/`campaign_period_to`, в сообщении — строка «Акция: … действует до
   30.09.2026». У бессрочных («до уведомления») дата не пишется, у Lex строки нет.
   Внутри `compute_combo` ветки успеха собираются через `dataclasses.replace(base, …)`,
   чтобы «паспорт» кампании не терялся.

10. **Аудит честности подарка (та же сессия, вечер).** Три бага переобещания,
    пойманные «злыми» тестами до фикса: (а) исключённые позиции (домино/соло-СВЧ)
    приближали порог подарка по числу категорий; (б) они же входили в сумму для
    порогов «на сумму N руб»; (в) подарочная позиция обнулялась даже когда без неё
    порог не выполнялся — «купи 1 прибор, получи холодильник за 90 000 бесплатно».
    Правильная семантика подтверждена эталоном Stefany (ПММ шла ПЯТОЙ при пороге 4 —
    порог выполняли 4 оплаченных) и кодом спеццены (others без спец-предмета).
    Теперь: валуер считает порог по УЧАСТВУЮЩИМ позициям; обнуление разрешено только
    если валуер на оплаченном остатке даёт ту же модель; иначе — manager_review без
    выдуманной выгоды. `_preferred_promo_models` целится в порог positions−1.

11. **E2E комплектов на проде: 12/12.** Новый `scripts/kit_e2e_suite.py` гоняет боевой
    поток (LLM-разбор → select_kit → format_kit → PDF) на реальных формулировках;
    автопроверки: покрытие, бренд из пятёрки, ограничение брендов клиента, позиции
    менеджеру, инварианты денег (итог = сумма − выгода ИЛИ подарок сверху), размер PDF.
    Прогон подтвердил фиксы: домино не приближает порог подарка, отдельностоящий
    холодильник участвует в «Формуле выгоды», ПММ KDI 45140 обнуляется при 4 оплаченных.
    Найдено и исправлено: замена дороже бюджета клиента шла БЕЗ пометки («до 30000» →
    молча 40 990) — теперь kit_builder ставит reason, format_kit показывает «⚠ Дороже
    бюджета…». Отчёт: data/out/kit_e2e_report.html (+ kit_e2e.json) на сервере.

## Следующий шаг
**Живой прогон на проде** (единственное, что отделяет заказчика от результата):
`git pull` → `bash deploy/update.sh` → `bash deploy/install-cron.sh` →
`python scripts/crawl_promos.py` (наполнить промо-таблицы прод-базы) →
`KIT_MODE=true` в `.env` → рестарт. Затем проверить на реальном каталоге: сборку
комплекта, выбор бренда/акции и PDF.

Дальше по остаткам: ссылки «Инструкция/Схема» в PDF, сверка вёрстки HTML-PDF с
эталоном на реальных данных, смена root-пароля VPS.

**Пагинация — вопрос закрыт, задачи нет.** `crawl_category` обходит все страницы
категории (`?PAGEN_1=N`, до `_MAX_PAGES`, параллельно), поэтому кандидаты из кэша
полные и акционная модель в них есть. Первой страницей ограничен только живой обход —
фолбэк при холодном/протухшем кэше; при работающем cron он не задействован. Старая
заметка «осталось: пагинация» в README относилась именно к фолбэку и вводила в
заблуждение — исправлена.
